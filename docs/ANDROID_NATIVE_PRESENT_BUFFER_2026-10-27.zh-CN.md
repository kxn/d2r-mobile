# 应用内原生尺寸出图与微小黑边清屏对照

本轮补上此前没有隔离的出图差异。相同 1968×900 游戏输出、0.85 3D 比例下，当前实现先放大到 2358×1080 的交换链；上游在 1968×900 缓冲中出图，再由 Android 合成缩放。本次只改应用 Surface 的缓冲尺寸，**没有再改系统 wm size，也没有降低游戏输出或 3D 比例**。

结果：应用内缩小缓冲约减少 9.5% 的原厂 GPU 写入计数；进一步消除最多两像素的黑边导致的整图清屏后，写入约减少 **20.5%**，普通运行约 **40.42→40.93～41.16 FPS**。这是可保留的带宽/操作量优化，尚不能解释或解决全部上游差距，也没有温度/能耗实测结论。

## 实现与条件控制

`c245fd8` 增加默认关闭的 `--native-buffer-geometry` / `--no-native-buffer-geometry`，JNI 在启动前固定，后端首次读取并缓存选择。只使用 NDK 的 `ANativeWindow_setBuffersGeometry`；官方 NDK 28.2 的头文件明确说明缓冲像素数与屏幕窗口尺寸独立，合成阶段负责缩放，0/0 恢复窗口基准尺寸。没有依赖驱动私有扩展。

源 crop 先按原规则验证，再请求缓冲尺寸；输出变化才重建交换链，保留旧 GPU/WSI 排空与真实同步。Surface 替换时旧工作排空后恢复原窗口几何；不支持时回退原 View 缓冲，避免每帧重试。窗口实际交换链范围、成功显示后的 game/surface 输出，以及原后端日志分别核实，不能把启动参数当实际尺寸。

第一版保留原 View 空间的长宽比/黑边，映射到新缓冲后按原归一化坐标处理输入。第二版 `7beef44` 只对 View 上总共不超过两像素的尺寸取整空隙铺满输出；较大黑边继续保留。该场景原来上下各约一像素的黑边会触发整张交换链 clear 和重叠写屏障；第二版实际后端记录 `applied=1968x900 content=0,0 1968x900`，原分支由完整 blit 覆盖全部像素，无需先清屏。这是有界的轻微显示比例取舍，不是像素级无差异声明。

两组都显式 `--reference-present`，禁止因新尺寸恰好符合条件而自动改用已有 shader-present 路径。其他条件固定：Q735 / Adreno 735、f830 Turnip prefer_sysmem、原 native 资源及 shader chain `29e56b51bce5`、共享/lazy/精确字节依赖、原调用者内翻译、CPU mask 0x80、stream splitting OFF、普通 mode 0、worker QoS OFF。

保持物理 1260×2750、用户原 override 1080×2358；Android View 为横屏 2358×1080。双方原游戏输出均 1968×900，3D 比例均 0.85；实际 API 的主 3D 区域为 1673×765。没有更换游戏逻辑、原加工模块、Shader、资源包或驱动。沿用 ARM64 原生执行与原 HLE。

## 生命周期资格尚未通过，保留候选

C1、C2 的性能与 SDK 窗口均在生命周期检查之前完整结束，实际模式/稳定状态/轨迹/原厂数据保留；后继 QA 失败不能被写成整个性能采集失败，也不能被抹去。

- C1 原 save helper 的 `--resume` 只检查 PID 存活，后继 attach 超时，没有证明真正恢复。最终原生命周期 save2 后停止。故不把 helper 的 resumed_same_process=true 当作通过。
- C2 追加前台 Activity、tick/time 增长和实际尺寸检查，仍未满足完整条件。原日志确有图形恢复、Surface 重建到 1968×900，并继续到后继 save2；但当前记录不足以排除既有生命周期/辅助脚本行为，也不足以宣称候选恢复没有问题。没有用营地截图替代这项验收。
- C1 的人工追查命令与控制器退出发生竞态，另启动了 PID 2386 的裸默认 Intent，缺少实验要求的 native pack/shared 启动组合，原生模块在资源准入时明确失败。原日志另存，不把它算作普通桌面或性能候选的成功运行。该进程已退出，没有为保存重新启动。

因此候选保留、默认关闭，原因是恢复资格未完成，**不是因为 FPS 没有大幅上涨**。下一步应先对同 APK 的关闭组做相同恢复检查，分清候选与原流程，再决定默认发布；不用新增玩法/地址补丁掩盖问题。没有修改或削弱正常桌面 APK/profile 校验。

## 对后续 CPU 研究的重要修正

重新核对已有六帧实际 API：当前是 **1 次 Begin/EndQuery 每帧，上游是 48 次**，不是两边都只有一次。上游源码仍按连续 run 合并查询；我们的预分析额外付费也确实消除了查询，不能把约 6.09M 规划指令全部视为无用工作。

最早 NOPLAN 的 33～35 FPS 对照在假页 GPU 依赖修复和 prefer_sysmem 默认策略之前，不能当作当前约 41 FPS 下的净成本结论。若重新测试，应明确衡量“去掉规划 vs 恢复查询/保守附件/普通状态解释”的总成本，并记录 API/PMU/实际出图，而不是直接删除预分析或重做同一套末端缓存。
