# 上游约 43 FPS 与当前约 34 FPS：整条路径的差异调查

状态：**此前显著差距的主要根因已定位、修复并完成真机发布。** 当前相同游戏尺寸/比例下，本实现两次 42.49 FPS，上游 43.18 FPS；仍有约 1.6% 的残差未逐项归因，不能称纯后端同条件胜出或全场景性能优化完成。下文第一至十三节保留各阶段当时的状态，当前结论以第十四、十五节为准。调查依据是真实执行路径、调度轨迹和原厂 GPU 计数，不从个别叶函数频率推断全部成本。

第一至六节主要使用实验分支 `codex/inline-shared-translation-v1` 的 `480ce73` 构建（APK SHA `1d194bea3976975faa8dfb92db811111647c5e43d96b870ffe5fdd042c49dce7`），着色器链 `29e56b51bce5`。`9ed3304` 补充启动参数检查，`42b24aa` 补充 GPU 功能夹具，不冒充进入了该 APK。第七节追加了 `5652204` 的调用来源注释取证和 `a31af09` 的正式冷启动修复验证；原游戏 CPU 模块、native 资源和 shader 链未改变。各版本与成绩分别记录，不将实验脚本启动等同桌面版发布。

## 一、已分清：回放 CPU 工作与阻塞等待

保持同一台 Adreno 735、1968×900 输出、固定 3D 0.85、同营地位置、调用线程内翻译/CPU7、共享/native、异步 GPU 完成，以及关闭启发式分块提交。官方 Perfetto 启用已有 Android Trace 区间后，将区间与实际 `sched` Running 相交；只统计采集窗内完整区间。

| 现有区间 | 完整调用数 | 墙钟 ms/次 | CPU Running ms/次 | 非 Running ms/次 |
|---|---:|---:|---:|---:|
| NVN command replay | 664 | 15.322125 | 15.316135 | 0.005990 |
| submission planning（嵌套在回放中） | 665 | 1.745915 | 1.743527 | 0.002387 |
| Present 驱动调用 | 665 | 4.648587 | 0.508724 | 4.139863 |
| queue submit | 1330 | 0.095407 | 0.092888 | 0.002519 |
| submit queue lock | 1330 | 0.001183 | 0.001182 | 0.000001 |
| present queue lock | 665 | 0.001043 | 0.001042 | 0.000001 |
| completion command pool reset（另一线程） | 1330 | 0.398224 | 0.321423 | 0.076801 |
| CPU publish（另一线程） | 1330 | 0.032107 | 0.023084 | 0.009023 |

这支持一个明确修正：**当前营地中，回放的约 15.3 ms 主要是实际执行，不能归因于大量阻塞抢锁。** Present 中才有明显等待；它可能包含驱动/GPU/WSI，不据此指认某个锁或纯 GPU 着色时间。完成线程的区间可与主线程重叠，不能相加扣减。表中 planning 也不能再与 replay 相加。

四个预扫描对照窗口的原有计数增量均为：`readback_ranges=0`、`cpu_reads=0`、`cpu_submit_waits=0`、`cpu_pending_waits=0`、`upload_waits=0`；内部提交与 guest 提交增量相等，stream split 为零。这不是“所有场景都不等待”，但不能继续用大量回读等待解释这几个窗口。

官方 Simpleperf 另外实测了当前版及上游：每边 15 秒 DWARF/199 Hz、15 秒 FP/399 Hz，均无丢样，保存实际失败/不完整调用栈，没有 joiner 或合成祖先。FP 错误调用链比例很高，因此保留可见宿主前缀和准确叶 IP，不能称整棵游戏栈已完全恢复。符号使用对应 APK 提取并核对哈希的原 ELF，避免被后续构建覆盖。

当前主线程中，`mtl_sub_index` 包含子调用约占 8.17% / 8.52%；后继相同模式再采约 8.80%。`vk_shader_cpu_sources` 约 4.06%–4.82%。锁函数可识别叶样本约 0.77%–0.84%，上游约 0.17%–0.26%；该比例只描述用户态执行，不当作阻塞等待。阻塞范围以本节调度相交结果为依据。

## 二、代码差异与已经执行的反证实验

上游同线程模式也保留 `x_push`、任务编号、队列锁、Present 票号和 `x_wait`，所以不能只发现我们有这些名字就认定它们制造了差距。

真正明确的差异是：我们的 `mtl_sub_index` 会完整展开命令流，建立深度/模板、Store、query liveness 和状态段索引。上游相应入口不做这次扫描。我们在共享/native 路径中还提前枚举 CPU 图像来源；实际绑定、图像准备及 GPU 使用记录继续在后面进行。上游描述符路径本身仍有快照和资源处理，因此不能把我们完整 binding 职责都称作多余。

为分清扫描的成本及其消费者收益，新增默认关闭的 `--submission-plan-reference`：跳过整提交预扫描，保留全部 NVN 命令、真实同步与 GPU 完成；深度、Store、查询等使用原保守回退，状态段及可选前瞻消费者不再命中。没有通过省掉游戏内容提速。

功能验证复用了原颜色、深度/模板 GPU 内容测试，覆盖多句柄、CALL/JUMP 返回和跨提交，46,169 项通过；原优化命中断言没有被改成永远通过，而是给保守路径单列内容验收。启动工具 17 项测试通过，附加开关不能用于接管正在运行的进程。该夹具不代替游戏全场景验收。

| 顺序 | 预扫描 | FPS | 主线程 Running ms/上屏帧 | 主线程运行加权 MHz | 管线数 |
|---|---|---:|---:|---:|---|
| NOPLAN1 | 关闭，保守回放 | 35.51 | 23.35 | 1853.09 | 260→260 |
| PLAN1 | 开启 | 33.52 | 22.92 | 1241.73 | 264→264 |
| NOPLAN2 | 关闭，保守回放 | 35.42 | 23.77 | 1877.94 | 260→260 |
| PLAN2 | 开启 | 33.07 | 23.01 | 1257.47 | 264→264 |

两个关闭组均更快上屏，但 **Running 未降，而且频率高出很多，不能宣称删除了同等比例 CPU 工作**。新采样确认扫描消失后，普通回放、binding、纹理使用记录和分配/回收的份额增加。关闭扫描也关掉了状态段和可选前瞻优化，这就是必须测净成本的原因；不能只扣除旧扫描比例。截图未发现明显黑块，真实游戏每轮均原生命周期 fresh save `commits=2` 后停止；保守路径仍为诊断选项，没有改成产品默认。

另单独关闭 pixel-local 通道融合而保留扫描，得到约 33.56 FPS、主线程 22.63 ms、1255 MHz。这一组没有解释明显差距，不拿整体关闭扫描的收益归给通道融合。

## 三、频率与测量条件：不能以毫秒不变认定没省工

新的上游可调试壳保持 release native library 字节相同，在相同营地/0.85 下再得到 **43.19 FPS**、主线程约 **18.96 ms**、约 **1669 MHz**。普通当前版约 33–34 FPS、23 ms、1250 MHz。频率差是真实混杂因素，不能按 MHz 线性归一后冒充硬件周期/指令证明。

已实际尝试 Android 官方 fixed performance mode，命令接受，脚本始终自动恢复普通模式。但两臂仍出现约 1085 / 1946 MHz，出图也大幅不同，**没有达到可当成同频实验的条件**，不使用这批数据估净收益，也不将低帧组报作日常回归。原始失败条件和恢复收条保留。

现有公开 ADPF 开关也已实测，API 可用、session/report 成功、无错误；得到约 33.55 FPS、主线程 22.55 ms、1321 MHz，没有解决差距。当前报告的工作预算约 14.8 ms，只覆盖提交翻译，而非整条游戏提交线程的全部帧工作；它不能证明整帧已经满足 16.7 ms，后续若调整提示范围须单独验证，不能把它混入删工收益。

Simpleperf 的 `--trace-offcpu` 在本机实际失败：系统工具报告 `sched:sched_switch` 事件不可用。没有据此另写离 CPU 采样器；等待分析使用上面实际取得的 Perfetto 调度和已有区间。上游 release 的 `XTRACE` 只对 Harmony 编译启用，Android 为 no-op，不能伪称已经取得上游相同命名区间。

当前已经关闭启发式分块提交，所以不能继续用历史的八次提交解释这一组差距。上游有约 113 次/帧 ALL_COMMANDS→ALL_COMMANDS barrier；我们主要使用资源/阶段依赖。因此也不能认定上游更快源于更细的同步。两端主 3D Render Area 都为 1673×765，主要附件格式一致，包含 B10G11R11、RGBA16F、RGBA8 和 D24S8，没有发现我们把主要 HDR 附件意外扩大格式。

按实际 Render Area×格式字节数，对要求 LOAD/STORE 的附件作全区域逻辑估算，当前约 LOAD 122.76 / STORE 166.21 MB，上游约 237.55 / 237.55 MB。这是未计压缩、覆盖、片上复用和驱动优化的逻辑面积估计，**不是总线流量**。其方向与前节全局实测流量不同，说明必须继续核对驱动执行，而不能只数 Store 或只按 API 数量预测 GPU 成本。

两边仍分别是定制 Turnip/native ASTC 与系统 Qualcomm/BC 的产品路径；没有将驱动与资源这个混杂因素称作纯后端代码差异。设备创建记录中两端均开启 robustBufferAccess，也没有据此找到单边额外边界检查的证据。结构结果、直接提取的对象和执行命令见 `api-tools/{own,upstream}-analysis/` 与 `api-tools/structural-comparison.json`。

有界追加的六次冷启动探测均未再命中慢状态，各次均确认存档、停止并恢复属性。仅使用原有 game-state 作为是否继续抓工具数据的触发条件，没有将这些短探测当作六个新的官方 FPS 成绩，也没有借此声称异常已消失。当前已经定位到额外提交/队列完成等待这一类路径，尚未拿到慢状态调用栈，不能指认具体调用者，更不能擅自删掉等待。

## 七、已证实的残留假依赖：CPU 图像读取被扩大到邻居 GPU 写入

前述“尚未取得慢状态调用栈”是当时状态。后继使用 `5652204` 给**已有官方 Perfetto 等待区间**增加调用者名称；只有原等待区间真的启用时才加入嵌套名称，没有新计时器、采样器或自定义 GPU 时间。原因是本机 Simpleperf 离 CPU 栈确实不可用、原 Perfetto 只有等待时长；原 LLDB 仍用于资源/范围检查。原 GPU 完成/资源重置夹具通过 529,514 项，未改变等待/发布语义。

新的慢窗口中，327 次长等待全部来自 `vk_pool_shared_cpu_observe_prepare`。正式 LLDB 调用栈进一步定位到：`vk_draw_record_impl → vk_shader_cpu_sources → texture_cpu_preflight → vk_pool_cpu_observe_prepare → vk_pool_shared_cpu_observe_prepare`，是绘制前的 CPU 图像源准备，不是 NVN guest fence、WSI 取图或资源重置锁。

LLDB 取得的一个实际例子为：CPU 源 13,312 字节，按页扩大后 16,384 字节；同一 pending submission 中的 GPU publication 长 65,536 字节，结束于 CPU 源之前 **48 字节**。二者真实字节范围完全不相交，仅与扩大的页范围相交。见 `.local/logs/queue-wait-origin-v1/false-page-hazard.json`。该快照的 CLI Pool 属性表达式因上下文选择失败而没有取得，未将其伪称为属性证明。

随后另一个慢进程取得了独立的完整证明：CPU 源 5,120 字节、页范围 8,192 字节；GPU publication 5,120 字节，起点在 CPU 源结束后 **208 字节**。该 Pool 实测内存属性为 `0xf`，具备 HOST_COHERENT；整个页包络位于同一存活 Pool，存在真实导入。相交项全为 shared GPU publication，实际 CPU 源与所有这些写入均不相交，没有相交的 CPU completion effect。

根因在于原保守检查把两类依赖混到同一个页包络：CPU 写回/保护确实涉及整页，而缓存一致的 GPU 写入只应与 CPU 真正要读的字节比较。即使没有一字节重叠，原路径仍将当前 recording 中途提交，并等待它全部 GPU 工作完成，破坏异步流水线。`readback_ranges/cpu_reads/upload_waits=0` 未覆盖这条路径，不能据此证明没有等待。

当前顺序改为实际写入与带宽优先，不继续叠加末端 CPU 缓存。相同 1968×900/0.85 基准下，用同一 `3eec36b` APK 完成局部读取/炫光开关的四组原厂计数器对照，总写均约 52.25～52.43MB/帧，FPS 40.88～40.96，没有证据把残余差距归成这两项优化，均保留默认开启。

`3c88c4c` 独立修复普通 View 尺寸出图中“一两行舍入黑边导致全图清屏”：铺满至多两像素/轴的余量，保留真正 letterbox。真实游戏 E1 官方窗口为 40.821FPS、55.362MB 写/帧；对照历史同输出/同 View 的 A4 65.580MB，约少 15.6%，没有宣称同等 FPS 增长或同 APK 交错 A/B。该修复不需要启用 native-buffer-geometry，也不改变游戏分辨率/3D 比例。

新 APK `54e724be74b6c227dd6f3dfa6f7a290a63de4396cee3cc285398e9d7835d50a7` 已完成两次普通图标冷启动、真实营地和原 save2/停止，匹配 profile/receipt 已发布。日常配置仍为 2358×1080/0.75，这个配置本来没有上述细边，因此不把基准的 15.6% 当作日常既得收益。native-buffer-geometry 仍默认关闭；关闭候选的参考组也存在辅助命令未真正恢复前台的问题，旧恢复失败不能直接归因于候选。

进一步优先从当前日常配置的渲染目标写回、复制与实际压缩状态查找大块写入，使用已有 API/原厂数据与必要的候选对照。记录见 [GPU 写入专项](ANDROID_GPU_WRITE_REDUCTION_2026-10-27.zh-CN.md)，原始记录 `.local/logs/write-path-policy-v1/`。

后继已实现应用内尺寸隔离，并发现细黑边导致的整图清屏。固定游戏输出/3D 比例、系统尺寸与显式 blit 后，原厂 GPU 写入约 65.58→52.06～52.10MB/出图间隔，少约 20.6%；同 APK 普通基准 40.42，候选 40.93～41.16 FPS。候选恢复资格尚未通过，保留而不默认发布；不是因涨帧小而丢弃其明确的工作量收益。完整顺序、实际构建、原厂窗口与失败边界见 [应用内原生尺寸出图对照](ANDROID_NATIVE_PRESENT_BUFFER_2026-10-27.zh-CN.md)。

## 13. 实测减少输出写入并发布应用内压缩

原驱动布局确认主 HDR/深度等附件已为 UBWC，四张日常 2358×1080 交换链却为线性。覆盖 Android loader 实际使用的 AHB 用途查询后，系统 allocator/mapper 能分配并导入真实压缩输出；未降 0.75 3D 比例、未改 shader 或游戏逻辑。四轮同 APK 交错对照：平均写入 **61.686→51.061 MB/完整出图间隔，少 17.22%**，读取少 8.49%，FPS **38.695→39.974，约高 3.31%**。均为原厂全局 GPU 计数器，包含合成，不是纯 NVN 带宽；未证明长期降温或全场景 60 FPS。

## 14. 当前同游戏尺寸对照与上游压缩确认

补齐当前 1968×900/0.85 游戏设置，当前两次官方窗口 42.490/42.495 FPS、44.788/44.730 MB 写/完整出图间隔，新上游 43.179 FPS、45.693 MB。当前平均写入约少 2.04%，FPS 仍低约 1.59%；目前已没有早先的明显总写入劣势。交换链尺寸、driver、纹理编码和 HUD 仍不同，不能把这组结果写成严格后端单因素对照。系统 mapper 的实际上游 SurfaceView 明确 `compressed: true`、HWC 为 `RGBA_8888_UBWC`，确认此前输出压缩修复是在补齐对方系统驱动已有的路径。

共享/lazy 343 MiB 已用 Pool 范围不进入旧脏页扫描比较/上传分支，新窗口旧 Pool 上传、回读及相应等待计数均为零；GPU 写计数不包含 CPU memcpy。当前整应用 Running 35.4/36.0 对上游 38.3 ms/间隔，最忙线程 18.9 对 18.7 ms、运行频率约 1.61/1.65 对 1.71 GHz，没有共享单开关合法因果对照，不能将所有 CPU 差异归于共享。剩余资源/依赖准备仍须按当前宏观预算研究。

既有 deferred-mip 候选在实际六帧中确实延续 HDR 通道，49→48 Pass、逻辑 STORE 少约 15.36 MB，但日常同 APK 官方实际写入仍约 51.26/51.10 MB，未证明同量级物理带宽节省。保留候选，下一步需拆准入管理成本及实际 GMEM 适用条件，不能仅按逻辑字节算收益，也未因未涨帧删掉。完整数据、压缩原文、CPU 指标范围和日常配置复核见 [同设置写入与共享 CPU 报告](ANDROID_MATCHED_WRITE_AND_SHARED_CPU_2026-10-27.zh-CN.md)。

## 15. 当前同步复核与根因结论

对目前发布的 6f3b131/B3 原生游戏再次使用官方 CPU-clock、PMU 与 Perfetto，未重建或更换运行库。当前匹配设置窗口 MEMPCA1 的 846 次完整重放：墙钟 12.3245 ms、Running 12.3199 ms、非 Running 0.0046 ms；规划墙钟 1.3379 ms，非 Running 0.00005 ms。提交队列锁与 present 队列锁分别 1.029 / 0.946 微秒/次，未出现 `Vulkan CPU waits queue completion` 区间。present 仍有约 2.0154 ms 非 Running，不能称 CPU/GPU 所有等待已消失。完成线程 pool reset 约 0.2955 ms/次、CPU publish 0.0203 ms/次，在另一线程执行，不能相加为主线程耗时。

同时重新核对两端实际代码：上游同线程路径仍保留 `g_xmu`、job/ticket 与 `x_wait`；上游 Vulkan engine 已有异步 pool-reset worker，也用互斥量交接工作。在本实现 `completion_thread()` 中，取出 pending 后先释放 `completion_mu` 再 `vkWaitForFences`；锁外等待这一点在当前源码中成立。不能以发现锁、完成线程或者函数名称作为巨量主线程等待的证据。

原先显著差距的可核查原因可归为三项，彼此收益不直接相加：

1. **共享内存观察范围错误。** 将一致性 GPU 字节依赖扩大到主机页，导致互不重叠的邻居资源也强制提交并等完成。第七节同 PID、同地址布局实验将约 31.8 ms/周期的假等待消掉，16.20→40.35 FPS；真实重叠和 CPU 页副作用保护保留。这是实现错误，不是 GPU 算力不足。
2. **本机 Turnip 的渲染模式选择。** 默认 bandwidth 与 prefer_sysmem 的实际完整窗口约 33.56→40.26 FPS；上游走系统 Qualcomm，不能假定两条 driver 路径会自动选同样的执行方式。现已把 qualified 策略放入应用自己的冷启动配置。没有证明所有移动 GPU、所有 pass 都应该强制 SYSMEM。
3. **Android 输出压缩路径没有接全。** 本实现实际交换链为线性，而上游系统 allocator 分配的是 UBWC。覆盖真实 loader 的用途查询并保留 allocator 决策后，日常四轮同 APK 对照写入少 17.22%、FPS 高 3.31%。压缩不是新增有损纹理处理，也不靠降低游戏渲染比例。

此外，细边导致整图清屏与查询无操作触发附件重做均有独立结构/工作量证明，已修复；不能将受控参考模式或特定输出尺寸下的收益重复计算进当前默认营地成绩。整提交规划确实是额外 CPU 工作，但其消费者也消除了 GPU/状态工作，关闭整段的净结果不支持作为免费收益；已保留独立参考实验。

当前硬件计数又证实所有者线程有约 26% 的用户态周期属于访存相关后端停顿，但这不等于 DRAM 饱和，也不是仍有旧整池扫描/上传。资源绑定、源检查和规划仍有可研究的工作预算，详见 [当前 CPU 访存与宏观预算](ANDROID_CPU_MEMORY_STALL_2026-10-27.zh-CN.md)。源码还确认 CPU 源预检未利用后继上传已有的 range-clean proof；这是约不足 1% 叶预算的小候选，尚未实现或报告收益，不把它当作此前大差距的根因。

本次任务的可验证结果是：在此前用于指认大差距的同机营地、同游戏尺寸/比例下，当前发布实现已从约 33–34 FPS 提升到 42.49 FPS，与实际上游 43.18 FPS 接近；之前的慢状态也有独立假依赖根因及冷启动修复证明。尚未逐项归因的约 0.69 FPS、不同 driver/WSI/贴图编码的混杂、所有场景 60 FPS 与长期温度，不冒充已解决。

最终只读复核见 `.local/logs/upstream-rootcause-final-audit-v1/current-deployment.json`：已安装 APK 与六个发布身份锚点和先前普通冷启动验收完全一致，生产源码自 6f3b131 后未变化，游戏与上游副本均已停止，系统尺寸/图层/调试属性恢复，perf_harden=1。当前同步复核原 SQL/CSV 和新原始采样保存在 `.local/logs/shared-owner-macro-v1/`，没有为收尾重新启动游戏。
