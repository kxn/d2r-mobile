# 上游约 43 FPS 与当前约 34 FPS：整条路径的差异调查

状态：**调查进行中，尚未证明全部差距的根因，不代表优化目标完成。** 这次以真实执行路径、调度轨迹和原厂 GPU 计数作比较，不再从个别叶函数频率推断全部成本。

当前手机安装的是实验分支 `codex/inline-shared-translation-v1` 的 `480ce73` 构建（APK SHA `1d194bea3976975faa8dfb92db811111647c5e43d96b870ffe5fdd042c49dce7`），原游戏 CPU 模块未改变；着色器链 `29e56b51bce5`。后继 `9ed3304` 补充启动参数检查，`42b24aa` 补充 GPU 功能夹具，不冒充已经进入该 APK。代码已备份至 fork。

## 一、已分清：回放 CPU 工作与阻塞等待

保持同一台 Adreno 735、1968×900 输出、固定 3D 0.85、同营地位置、调用线程内翻译/CPU7、共享/native、异步 GPU 完成，以及关闭启发式分块提交。官方 Perfetto 启用已有 Android Trace 区间后，将区间与实际 `sched` Running 相交；只统计采集窗内完整区间。

| 现有区间 | 完整调用数 | 墙钟 ms/次 | CPU Running ms/次 | 非 Running ms/次 |
|---|---:|---:|---:|---:|
| NVN command replay | 664 | 15.322125 | 15.316135 | 0.005990 |
| submission planning（嵌套在回放中） | 665 | 1.745915 | 1.743527 | 0.002387 |
| Present 驱动调用 | 665 | 4.648587 | 0.508724 | 4.139863 |
| queue submit | 1330 | 0.095407 | 0.092888 | 0.002519 |
| submit queue lock | 1330 | 0.001183 | 0.001182 | 0.000001 |
| present queue lock | 665 | 0.001043 | 0.001042 | 0.000001 |
| completion command pool reset（另一线程） | 1330 | 0.398224 | 0.321423 | 0.076801 |
| CPU publish（另一线程） | 1330 | 0.032107 | 0.023084 | 0.009023 |

这支持一个明确修正：**当前营地中，回放的约 15.3 ms 主要是实际执行，不能归因于大量阻塞抢锁。** Present 中才有明显等待；它可能包含驱动/GPU/WSI，不据此指认某个锁或纯 GPU 着色时间。完成线程的区间可与主线程重叠，不能相加扣减。表中 planning 也不能再与 replay 相加。

四个预扫描对照窗口的原有计数增量均为：`readback_ranges=0`、`cpu_reads=0`、`cpu_submit_waits=0`、`cpu_pending_waits=0`、`upload_waits=0`；内部提交与 guest 提交增量相等，stream split 为零。这不是“所有场景都不等待”，但不能继续用大量回读等待解释这几个窗口。

官方 Simpleperf 另外实测了当前版及上游：每边 15 秒 DWARF/199 Hz、15 秒 FP/399 Hz，均无丢样，保存实际失败/不完整调用栈，没有 joiner 或合成祖先。FP 错误调用链比例很高，因此保留可见宿主前缀和准确叶 IP，不能称整棵游戏栈已完全恢复。符号使用对应 APK 提取并核对哈希的原 ELF，避免被后续构建覆盖。

当前主线程中，`mtl_sub_index` 包含子调用约占 8.17% / 8.52%；后继相同模式再采约 8.80%。`vk_shader_cpu_sources` 约 4.06%–4.82%。锁函数可识别叶样本约 0.77%–0.84%，上游约 0.17%–0.26%；该比例只描述用户态执行，不当作阻塞等待。阻塞范围以本节调度相交结果为依据。

## 二、代码差异与已经执行的反证实验

上游同线程模式也保留 `x_push`、任务编号、队列锁、Present 票号和 `x_wait`，所以不能只发现我们有这些名字就认定它们制造了差距。

真正明确的差异是：我们的 `mtl_sub_index` 会完整展开命令流，建立深度/模板、Store、query liveness 和状态段索引。上游相应入口不做这次扫描。我们在共享/native 路径中还提前枚举 CPU 图像来源；实际绑定、图像准备及 GPU 使用记录继续在后面进行。上游描述符路径本身仍有快照和资源处理，因此不能把我们完整 binding 职责都称作多余。

为分清扫描的成本及其消费者收益，新增默认关闭的 `--submission-plan-reference`：跳过整提交预扫描，保留全部 NVN 命令、真实同步与 GPU 完成；深度、Store、查询等使用原保守回退，状态段及可选前瞻消费者不再命中。没有通过省掉游戏内容提速。

功能验证复用了原颜色、深度/模板 GPU 内容测试，覆盖多句柄、CALL/JUMP 返回和跨提交，46,169 项通过；原优化命中断言没有被改成永远通过，而是给保守路径单列内容验收。启动工具 17 项测试通过，附加开关不能用于接管正在运行的进程。该夹具不代替游戏全场景验收。

| 顺序 | 预扫描 | FPS | 主线程 Running ms/上屏帧 | 主线程运行加权 MHz | 管线数 |
|---|---|---:|---:|---:|---|
| NOPLAN1 | 关闭，保守回放 | 35.51 | 23.35 | 1853.09 | 260→260 |
| PLAN1 | 开启 | 33.52 | 22.92 | 1241.73 | 264→264 |
| NOPLAN2 | 关闭，保守回放 | 35.42 | 23.77 | 1877.94 | 260→260 |
| PLAN2 | 开启 | 33.07 | 23.01 | 1257.47 | 264→264 |

两个关闭组均更快上屏，但 **Running 未降，而且频率高出很多，不能宣称删除了同等比例 CPU 工作**。新采样确认扫描消失后，普通回放、binding、纹理使用记录和分配/回收的份额增加。关闭扫描也关掉了状态段和可选前瞻优化，这就是必须测净成本的原因；不能只扣除旧扫描比例。截图未发现明显黑块，真实游戏每轮均原生命周期 fresh save `commits=2` 后停止；保守路径仍为诊断选项，没有改成产品默认。

另单独关闭 pixel-local 通道融合而保留扫描，得到约 33.56 FPS、主线程 22.63 ms、1255 MHz。这一组没有解释明显差距，不拿整体关闭扫描的收益归给通道融合。

## 三、频率与测量条件：不能以毫秒不变认定没省工

新的上游可调试壳保持 release native library 字节相同，在相同营地/0.85 下再得到 **43.19 FPS**、主线程约 **18.96 ms**、约 **1669 MHz**。普通当前版约 33–34 FPS、23 ms、1250 MHz。频率差是真实混杂因素，不能按 MHz 线性归一后冒充硬件周期/指令证明。

已实际尝试 Android 官方 fixed performance mode，命令接受，脚本始终自动恢复普通模式。但两臂仍出现约 1085 / 1946 MHz，出图也大幅不同，**没有达到可当成同频实验的条件**，不使用这批数据估净收益，也不将低帧组报作日常回归。原始失败条件和恢复收条保留。

现有公开 ADPF 开关也已实测，API 可用、session/report 成功、无错误；得到约 33.55 FPS、主线程 22.55 ms、1321 MHz，没有解决差距。当前报告的工作预算约 14.8 ms，只覆盖提交翻译，而非整条游戏提交线程的全部帧工作；它不能证明整帧已经满足 16.7 ms，后续若调整提示范围须单独验证，不能把它混入删工收益。

Simpleperf 的 `--trace-offcpu` 在本机实际失败：系统工具报告 `sched:sched_switch` 事件不可用。没有据此另写离 CPU 采样器；等待分析使用上面实际取得的 Perfetto 调度和已有区间。上游 release 的 `XTRACE` 只对 Harmony 编译启用，Android 为 no-op，不能伪称已经取得上游相同命名区间。

## 四、已取得当前两端原厂 GPU 计数

重新启动官方 Snapdragon Profiler 2026.9，在同一台手机实际选择并核实九指标；分别运行当前版本和原 native 库字节相同的上游可调试壳。使用官方 Perfetto clock snapshot 连接设备时钟与原厂样本时间，流量只积分在各自实际游戏 Surface 首末完整上屏区间，使用原验证和积分程序，不把 12 秒工具流量除以 8 秒帧数。

| 指标 | 当前版本 | 上游 |
|---|---:|---:|
| 实际上屏 FPS | 33.65 | 43.37 |
| GPU 时钟 MHz | 499.27 | 499.07 |
| 总读取 MB/完整上屏间隔 | 123.28 | 106.53 |
| 其中纹理读取 MB/间隔 | 91.42 | 86.32 |
| 总写入 MB/间隔 | 62.77 | 45.69 |
| 片元 M/间隔 | 29.52 | 26.19 |
| Shaders Busy，% | 64.24 | 80.19 |
| Texture Pipes Busy，% | 38.75 | 51.77 |
| Texture L2 Miss，% | 7.92 | 5.07 |

MB 是十进制。纹理读取属于总读取，不能相加。**两端 GPU 频率几乎相同，不能用上游 GPU 频率更高解释差距。** 当前每完整上屏间隔的写入、读取较高，接下来须核对真实通道、复制、附件 Store 和依赖边界。

这些计数是全局 GPU 数据，包含 Android 合成和 UI；固定频率的 UI 工作分摊到较少游戏帧上，也会增加每帧数值。不能直接把差值全部归给 NVN、把片元差称作游戏多画了同等比例，也不能将 Shaders Busy 与独立的时钟均值相乘冒充游戏独占着色周期。当前仍缺少能把额外写入对应到具体操作的结构证据。

上游对照的资源闭包重新逐文件校验：release 的原 overlay/module 包，加五个上游 inline-CS 规避 shader；没有混入最新生成 overlay。原参考在自己的包/存档克隆中运行，不覆盖用户原存档。两个游戏、原厂 GUI/Xvfb 与 13 个本次 collector 均已停止。原 close 报过一个 collector 在身份读取期间消失，原错误保留；独立后继收条确认全部本次工具已退出，层设置与采集前相同，没有停止无关系统服务。

## 五、两端六帧实际 API 结构已完成

复用现有 GFXReconstruct API-structure 层、官方 info/convert 以及原提交遍历程序。每端六次真实 Present，仅枚举 trim 恢复边界之后实际提交及递归执行的 secondary；不把定义但未提交的命令计入，不把捕获速度当 FPS，也不声称 imported host payload 已可重放。上游原捕获成功，第一次导出因旧辅助程序包名写死而失败；只对已关闭捕获修正导出包名，没有重新采帧，原失败与后继导出收条分别保留。

| 每帧实际执行 | 当前版本 | 上游 |
|---|---:|---:|
| Draw | 2416 | 2419 |
| QueueSubmit | 2 | 2 |
| BeginRenderPass | 49 | 54 |
| PipelineBarrier | 162 | 129 |
| ExecuteCommands | 49 | 0 |
| CopyImage | 2 | 3 |
| BlitImage | 2 | 1 |

当前已经关闭启发式分块提交，所以不能继续用历史的八次提交解释这一组差距。上游有约 113 次/帧 ALL_COMMANDS→ALL_COMMANDS barrier；我们主要使用资源/阶段依赖。因此也不能认定上游更快源于更细的同步。两端主 3D Render Area 都为 1673×765，主要附件格式一致，包含 B10G11R11、RGBA16F、RGBA8 和 D24S8，没有发现我们把主要 HDR 附件意外扩大格式。

我们的两次 CopyImage 是 256×256 深度和 32³ 颜色体积，不能据此编造全屏大复制。两次 Blit 分别为 418×191→836×382 的中间图和最终出图。上游也保留最终出图/黑边处理。当前使用延后确定 Load/Store 的 secondary 录制，上游在 primary 内直接录制；这是执行方式差异，尚不能仅按 49 次 ExecuteCommands 就认定其成本。

按实际 Render Area×格式字节数，对要求 LOAD/STORE 的附件作全区域逻辑估算，当前约 LOAD 122.76 / STORE 166.21 MB，上游约 237.55 / 237.55 MB。这是未计压缩、覆盖、片上复用和驱动优化的逻辑面积估计，**不是总线流量**。其方向与前节全局实测流量不同，说明必须继续核对驱动执行，而不能只数 Store 或只按 API 数量预测 GPU 成本。

两边仍分别是定制 Turnip/native ASTC 与系统 Qualcomm/BC 的产品路径；没有将驱动与资源这个混杂因素称作纯后端代码差异。设备创建记录中两端均开启 robustBufferAccess，也没有据此找到单边额外边界检查的证据。结构结果、直接提取的对象和执行命令见 `api-tools/{own,upstream}-analysis/` 与 `api-tools/structural-comparison.json`。

## 六、当前代码的 Turnip 渲染模式对照与慢状态

保持同一已安装 480ce73 APK、29e56 shader、shared/lazy/native 资源、调用线程翻译/CPU7、输出 1968×900、固定 0.85、关闭 stream split。只在冷启动改变 Mesa 原有模式属性：默认 BANDWIDTH 自动选择与强制 SYSMEM。每次均核实**本次 PID** 的官方 TU_DEBUG 启动位 1 / 9，然后停止 logcat；八次 distinct 稳定管线状态后再用原 20 秒 Perfetto 窗口测量。没有自己写采样器或计时器。

| 顺序 | 模式 | FPS | owner Running ms/帧 | 整应用 Running ms/帧 | owner MHz | 内部提交/guest |
|---|---|---:|---:|---:|---:|---:|
| DEFAULT1 | 自动 | 33.57 | 22.50 | 41.87 | 1319.76 | 1 |
| SYSMEM1R | SYSMEM | 40.19 | 20.13 | 37.96 | 1545.57 | 1 |
| SYSMEM2 | SYSMEM，慢状态 | 16.27 | 27.82 | 56.99 | 1091.71 | 2 |
| DEFAULT2 | 自动 | 33.58 | 22.55 | 41.69 | 1329.47 | 1 |
| SYSMEM3 | SYSMEM | 40.16 | 20.18 | 37.93 | 1563.68 | 1 |
| SYSMEM4 | SYSMEM | 40.22 | 20.03 | 37.74 | 1535.64 | 1 |
| SYSMEM5 | SYSMEM | 40.41 | 19.91 | 36.01 | 1563.71 | 1 |
| SYSMEM6 | SYSMEM | 40.21 | 20.11 | 37.92 | 1553.39 | 1 |

具体频率以 `mode-tools/results.json` 的原 CSV 汇总为准，不能用频率线性归一代替 PMU。各窗口管线数均为 256→256；部分窗口特化变体数为 30→32，其余 30→30 或 32→32，条件差异保留，不能称完全逐 draw 相同。排除两次发生特化增长的窗口后，默认模式仍为 33.58 FPS，SYSMEM 五个窗口均为 40.16–40.41 FPS；慢状态保留为实际异常，不因出现增长就丢弃。内部提交主要含出图，不等于额外 guest 帧；正常每周期共两次，慢状态共三次。

**正常状态下模式切换复现了约 20% 的 FPS 差异，接近本机上游约 43.4 FPS；但不能漏报 16.27 FPS 的重复窗口，更不能把它永久默认启用当作已解决。** 这是现有驱动模式实验的当前配置验证，不冒称新算法；10 月 24 日旧配置也曾出现类似敏感性。SYSMEM 仍由 GPU 绘制，不是 CPU 软件光栅，也不是共享内存开关。当前没有同窗 SYSMEM 原厂带宽/功耗结果，不能宣称已降带宽或温度。

这次最重要的新证据在慢状态。对三个窗口继续使用 Perfetto 既有区间与 sched Running 相交：

| 区间，ms/次 | DEFAULT1 | SYSMEM1R | SYSMEM2 慢状态 |
|---|---:|---:|---:|
| replay 墙钟 | 14.815 | 12.939 | 48.111 |
| replay Running | 14.813 | 12.930 | 17.331 |
| replay 非 Running | 0.002 | 0.009 | **30.780** |
| Present 墙钟 | 5.463 | 2.754 | 0.580 |
| Present 非 Running | 4.975 | 2.283 | 0 |

慢窗口 323 次 `Vulkan CPU waits queue completion` 合计约 9959.89 ms，即约 **30.84 ms/次**，同时每 guest 多一次内部提交。读回、CPU read、upload wait 等旧计数增量仍全为零；**这些计数没有覆盖所有内部等待，不能将“计数为零”当作没有同步的充分证据。** 第一节“不主要阻塞”的结论仅适用于当时正常窗口，不能外推到这次慢状态。不能先将其归因热降频、一个特定锁或 SYSMEM 本身；必须拿到真实等待调用路径。

在性能窗口之后实际尝试官方 debuggerd（要求 root，失败记录保留）与 LLDB。SYSMEM4 正常窗口内没有这个周期性等待，后继 LLDB 等断点时，复用的中断辅助脚本出现 Python debugger 上下文错误；性能采集已经完成，不覆盖其成绩，也不称已取得慢状态栈。后继修复调试脚本的上下文捕获，确认该失败会话已脱离、存档退出、属性恢复，再作有界冷启动慢状态复现；只在慢候选补 Perfetto/LLDB，不重复采集已知正常基线。

有界追加的六次冷启动探测均未再命中慢状态，各次均确认存档、停止并恢复属性。仅使用原有 game-state 作为是否继续抓工具数据的触发条件，没有将这些短探测当作六个新的官方 FPS 成绩，也没有借此声称异常已消失。当前已经定位到额外提交/队列完成等待这一类路径，尚未拿到慢状态调用栈，不能指认具体调用者，更不能擅自删掉等待。

## 下一步与证据位置

优先定位这次新增的“每周期一次内部提交并等待”调用来源及其必要的依赖；随后再优化正常状态下驱动通道选择与 CPU 准备。不能继续用所有正常窗口 15 ms 执行的结论掩盖慢状态约 31 ms 的真实等待，也不能把 CPU Running 降低直接写成已删除相同运算量。

当前全部原始数据位于 `.local/logs/inline-upstream-rootcause-v1/`：`owner-budget.json`、`planning-results.json`、`scope-cpu.sql/csv`、`WAIT1/`、`UPSTREAM-SCHED1/`、`fixed-mode-result.json`、`HINT1/`、`gpu-tools/comparison.json`、两臂原 `.sdp`/数据库/轨迹/SQL、`api-tools/`、`MODE-*/` 与 `mode-tools/`。性能窗口与后继调试失败分开保存；各已结束游戏均原生命周期确认存档后停止，驱动模式属性恢复原值。以上是实验结果与可排除项，不是“根因已经全部找完”的结论。
