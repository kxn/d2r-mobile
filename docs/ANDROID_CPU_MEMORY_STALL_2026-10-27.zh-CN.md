# 当前高通 CPU 访存与宏观预算

结论：降低 CPU 访存有实测依据，但尚不能将整个 Android 运行时定性为 DRAM 带宽饱和。当前工作应区分 GPU 流量、CPU 内存停顿与显式内存拷贝；三者不能用一个字节数代替。

## 测量范围

设备仍为 Q735（10CG570J59001U1），使用 6f3b131 构建 APK 与 B3 Turnip，游戏输出 1968×900、3D 比例 0.85，实际 Surface 2358×1080；共享/lazy Pool、应用内输出压缩开启，mip clear 实验关闭。没有修改源码、重建或重装 APK。本次没有使用 Mali 或平板。

官方系统 Simpleperf 对真实录制所有者线程采集；NDK ReportLib 解析原数据，符号来自实际部署的同哈希 ELF。Perfetto 分别记录无 PMU 与并发 PMU 窗口。脚本仅编排和整理现成工具输出，没有新增计时器或采样器。原始资料与 SHA256 清单在 `.local/logs/shared-owner-macro-v1/`。

## CPU 时钟采样复核

同一进程连续两段 15 秒 DWARF CPU-clock 用户态采样，各有 2267 / 2246 个所有者线程样本。下列为实际调用链包含子调用的比例，不能相加：

| 实际父路径 | DW1 | DW2 |
|---|---:|---:|
| draw 录制 | 41.69% | 41.81% |
| 资源绑定准备 | 15.22% | 14.25% |
| 提交前命令规划 | 7.54% | 7.52% |
| CPU 源资源预检 | 5.21% | 3.92% |
| 重放状态分段 | 4.68% | 4.99% |

显式 memcpy/memmove/memcmp/memset 等叶样本约占 4.4%–4.6%，并非全部访存成本。FP 采样与 DWARF 的祖先覆盖存在差异，部分驱动调用链不能展开到重放父节点；不将缺失祖先的样本全部解释为游戏业务。单独官方 PMU 与 Perfetto 交集仍约为每个完整 Surface 间隔 72.43–72.48 M 条用户态指令、28.28–28.31 M 周期，未观察到工作量已大幅降低却仅被 FPS 隐藏的证据。

## 两轮硬件访存计数

Simpleperf stat 对实际所有者 TID，分三组各 8 秒测量，完成两轮；活跃核均为 CPU7，事件 time_running / time_enabled 为 1.0，没有按多路复用缩放。不同组不伪装为同一时刻的联合计数。

| 用户态周期比例 | 第一轮 | 第二轮 |
|---|---:|---:|
| 后端停顿 | 34.38% | 34.19% |
| 其中 memory-bound 后端停顿 | 26.31% | 26.10% |
| 其中 CPU-bound 后端停顿 | 8.08% | 8.09% |
| 前端停顿 | 21.59% | 21.57% |

这些是处理器事件定义下的周期比例，不是可直接消除的整帧时间；前后端事件也不任意相加。CPU 的缓存、地址翻译、依赖链和外部内存延迟都需要区分，memory-bound 不自动等于共享 DRAM 已打满。

LLC read miss / LLC read 为 69.98% / 70.28%，分母不是所有 CPU load。核心到 SCU 的读数据 beat 为 35.01 / 34.76 M/s，写为 27.49 / 27.40 M/s；未将其乘一个未经核对的宽度冒充 DRAM GB/s。[Cortex-X4 官方手册](https://documentation-service.arm.com/static/6585aec6b52744113be620e8)说明 BUS_ACCESS 为核心与 SCU 间 beat，LL_CACHE_MISS_RD 的来源亦不局限于 DRAM。

## 按访存停顿事件定位实际流程

额外使用 Simpleperf `raw-stall-backend-membound:u`、每百万事件采样，并保留 DWARF 失败展开结果，不拼接推测祖先。32 秒记录与 20 秒官方 Perfetto 同时进行，通过 Perfetto 的 `to_monotonic()` 转换时钟，在完整 Surface 区间内保留 6296 个样本。按采样时刻落入的真实 Perfetto 切片归类，避免因驱动展开中断而丢失宏观范围：

| 实际切片范围 | 占访存停顿采样事件 |
|---|---:|
| 命令重放 | 42.01% |
| 提交前命令规划 | 8.48% |
| present | 1.21% |
| acquire | 0.30% |
| 队列 submit | 0.10% |
| 上述后端切片之外 | 47.90% |

后端之外包含未符号化 PC、游戏与宿主工作，不能全部称为游戏逻辑。以上为事件占比，不是各阶段耗时或 DRAM 流量；采样 PC 还有事件 skid，叶函数排名仅作定位依据。本次事件定位为单窗口，稳定性证据来自另行完成的两轮 stat 与两轮 CPU-clock，不能声称事件调用链也已重复采集。

显式内存函数合计占这批访存停顿事件 5.21%。实际重放路径可识别热点包括资源绑定准备、纹理查找/视图复用、CPU 源检查、描述符编码及驱动状态绑定；规划部分集中于命令遍历和纹理 footprint 查询。它们包含大量小块元数据访问，不应继续将 CPU 访存等同于旧 Pool 整片复制。

同一 MEMPCA1 Perfetto 使用原 `sched` 相交查询复核：846 次完整 replay 平均墙钟 12.3245 ms、Running 12.3199 ms、非 Running 0.0046 ms；规划 1.3379 ms，非 Running 0.00005 ms。队列提交锁/出图锁平均 1.029/0.946 微秒，未出现原 CPU 等队列完成区间。present 仍有约 2.0154 ms 非 Running，不能说已经没有任何 GPU/WSI 等待。原查询及结果为 `current-scope-cpu.sql/csv`。这份当前发布版本的证据支持继续研究实际 CPU 工作，不能拿旧慢状态的 32 ms 假等待反复解释当前正常窗口。

## 优先级及收益边界

1. 保留已验证的 GPU 输出压缩，并继续按真实硬件流量评估附件、纹理及 Pass 结构。既有对照 GPU 写入降低 17.22%，FPS 仅增加 3.31%，已经说明不是“写入少多少就一定快多少”的单一线性关系。
2. CPU 优先研究资源绑定准备和源检查的整体生命周期，降低重复元数据解析和工作集；当前 CPU-clock 父预算约 14%–15% 与 4%–5%，包含项不能重复相加。需要先证明可跳过的具体工作及有效期，再实验，不另堆一层同成本检查。
3. 命令规划约 7.5% 的执行预算稳定存在，可研究热数据布局/遍历；不能为省 CPU 直接关闭现有消除 GPU 工作的规划。此前关闭规划及代码布局候选的实测结论仍有效，不包装为新发现。
4. 不把 memcpy 的约 4%–5% 叶预算、shader hash 的约 1% 叶预算，或队列锁用户态叶样本包装为主要瓶颈。需要另看调度等待，内存事件不能证明锁阻塞。

现有共享 Pool 路径已跳过旧脏页扫描/快照比较/上传分支，当前窗口相关旧计数为零；共享后的资源依赖、地址覆盖和图像语义检查仍存在。GPU 写入计数不包含 CPU memcpy，CPU 访问减少的收益须由 CPU 指令、Running、访存停顿和整帧共同验证。

测量完成均通过原 Android 生命周期取得新 save2 存档确认，再停止游戏。perf_harden 恢复为 1，GPU 抓帧层未选择，调试属性为空。本次只新增分析文档，未改变生产包、驱动、原始游戏加工产物或默认配置。
