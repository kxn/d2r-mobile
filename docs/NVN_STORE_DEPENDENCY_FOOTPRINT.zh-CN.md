# 附件依赖索引的纹理内存范围

附件 Store 前瞻索引原先在每个 bucket 中保存完整的 `tex_t`。这个索引实际只读取纹理的 `serial`、`mem` 和 `L.size`：用于序号查找、地址排序和内存别名判断。描述符缓存未命中时，它还会先在注册表锁内复制完整的纹理对象，再复制进 bucket。

现在这个索引只保存上述三个字段的 24 字节值快照。描述符查询仍在 `V.resources` 锁内校验原来的 ID、容量、限制和有效位，然后复制这三个字段；不会保存指向可重新分配的注册表的指针。私有 bucket 从 160 字节缩小到 40 字节，4096 项静态数组从 640 KiB 缩小到 160 KiB。两种大小都有编译断言。

原有序号哈希、首次建桶顺序、描述符缓存、附件缓存、别名邻接表、事件顺序及 epoch 校验均保留。别名判断保留原条件：相同序号、空地址、相同地址，以及用地址差与大小比较的重叠判断。完整清屏仍使用原纹理尺寸，独立的原始命令扫描仍使用完整 `tex_t` 和原 `overlaps()`。NVN 对象、快照、资源生命周期和实际绘制均未改变。

依据是已有 e341 Simpleperf 采样：四个 `vk_texture_descriptor` 自身样本的调用者都是 Store 索引的 `descriptor_bucket`；其中三个落在有效位后的条件分支，一个落在纹理复制的存储指令。它们不等于四个样本都花在复制上，也不能据此估计帧率收益。

实际 Android NDK 28.2、API 29、O3、TLSdesc、保留帧指针及栈保护的前后编译确认：

| 项目 | 原实现 | 当前实现 |
| --- | ---: | ---: |
| bucket 数组 | 655360 B | 163840 B |
| 索引描述符查询的数据快照 | 144 B | 24 B |
| `mtl_sub_index` 代码 | 7924 B | 7632 B |
| `mtl_sub_index` 栈帧 | 41120 B | 41120 B |

新描述符查询保留同样的锁与有效性检查，数据部分只有三条 64 位加载和 24 字节存储；原来的完整查询仍供其他调用者与参考扫描使用。保持 `attachment_event_add` 的原热路径内联边界，没有新增逐绘制调用或辅助栈帧；这是因为编译器在早期候选中曾将它改为独立函数。两个实际编译单元的代码合计减少 120 字节，新窄查询本身增加 180 字节；其他完整查询调用者不受影响。代码尺寸变化不能代替动态 CPU 数据。静态数组减少的是保留空间和每个实际使用 bucket 的工作集，不能直接算成同等大小的 RSS 或硬件 DRAM 流量减少。

现有完整原 NVN 公共测试在 Lavapipe 上通过异步和串行两种模式，分别完成 22031792 和 21929813 项检查。测试启用 Khronos Validation 与同步校验，并保留 `DM_VULKAN_STORE_CHECK=1`，将索引结果与未修改的原始命令扫描核对；没有新增镜像实现测试或计时器。这些结果是宿主软件 Vulkan 正确性证据，不是 Android 游戏、帧率或温度结果。
