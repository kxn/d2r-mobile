# 单独隔离附件 Store 索引的成本

## 问题与预算

第七节假页依赖修复、内联翻译与 `prefer_sysmem` 生效后，先对当前 APK 做两次独立的官方 Perfetto + Simpleperf 采集，避免继续使用慢状态的旧权重。FAST1/FAST2 分别为 40.11/40.29 FPS，主线程 Running 20.12/19.45 ms/帧。官方源代码注解将 Store 索引文件归到主线程 CPU 的约 3.93%/4.15%；完整 planning 为约 1.4 ms，**不能把它全部当作 Store 索引预算**。实施前预估可省约 0.8 ms。

Simpleperf 使用系统工具 `cpu-clock:u`、399 Hz、FP、关闭 callchain joiner；每次约 4,500 个主线程样本。原游戏原生执行跨越的根栈不能完整展开，工具将所有根链标成 incomplete。这里仅使用已解析宿主原生段、叶指令和官方源码注解，不重建游戏栈，也不将 incomplete 隐藏成完整火焰图。FP 采样与 FPS 性能窗口分开。

## 实验实现

源码 `3d23f1b` 增加默认关闭的 `--keep-attachment-stores` 冷启动对照：

- 省掉 Store 事件收集、按资源排序与别名关联；需要 Store 决策时直接保留。
- 保留同一命令展开、深度/模板反向分析、查询 liveness、状态段和未来操作消费者。
- 不使用原 `store_reference`：该选项会退回逐目标扫描原命令，不能用于测量“完全不做 Store 分析”。
- 保留独立的只读深度/模板 `NONE`、清屏与加载消除；不是把全部渲染优化一并关闭。
- 选项只在 native 启动前设置一次，运行后 setter 拒绝修改，热路径不读取环境变量。

没有修改游戏模块、NSO 字节、shader、材质资源或世界状态。APK 由原构建入口生成，SHA256 为 `7f1ae63cf39c2b9c11db5b0760901e1165a45882a45b99639641f39b85f99ed8`；宿主 ELF 为 `60fdab4c7c2c551e103ff5f3d8073a493e8c9d05ce8e178091ad899601c5a7ad`。构建清单和归档位于 `.local/build/store-index-cost-v1/`。

既有实际 Vulkan 渲染夹具增加第三个 keep-store 分支，对完整/局部清除、采样、复制、多 mip/layer、深度/模板内容执行相同检查，并要求索引构建、查询、参考扫描和 fallback 数量均不增长。Linux Lavapipe + validation 共 **136,400 项通过**；这是 GPU 语义检查，不是 Android 游戏验收。首次执行写错本机 ICD 文件名而未启动，保留失败日志；第二次使用实际存在的 `lvp_icd.json` 通过。启动工具 22 项通过。

## 真机交错结果

同台 USB 高通、同一实验 APK、f830 驱动、native ASTC、shader 链 `29e56b51bce5`、共享/lazy/精确字节依赖、内联 CPU7、stream splitting OFF、1968×900 输出、固定 0.85、`prefer_sysmem`。所有正式窗口 PSO 256→256、特化 32→32，内部提交/guest 为 1。

| 冷启动窗口 | FPS | 主线程 Running ms/帧 | 主线程加权 MHz | planning Running ms/次 |
|---|---:|---:|---:|---:|
| A1：原 Store 分析 | 40.39 | 19.86 | 1537 | 1.452 |
| B1：跳过 Store 分析 | 40.26 | 19.79 | 1463 | 0.743 |
| B2：跳过 Store 分析 | 40.23 | 19.83 | 1440 | 0.761 |
| A2：恢复原 Store 分析 | 40.14 | 20.02 | 1572 | 1.483 |

B1 有一次主机读取已有 game-state 行的额外观测，单独记录，不能充当完全无干预的重复窗口；B2 没有这次观测。Perfetto 表明约 **0.7 ms 的 planning 工作确实消失**，而不是将它移到原始命令 fallback 扫描。每 guest 原约 **15,180～15,200 条 Store 索引事件变为 0**；查询消除仍约 2,420 draw/guest，并没有退化成全部保留查询。

**没有测到可靠涨帧。** 主线程其余部分的时间不能直接相减后称为“工作转移”：两组 CPU 频率不同。需要硬件指令计数进一步区分工作量、运行时间和 DVFS；不能将 MHz 简单相乘后冒充 PMU cycles。

### 用硬件计数复核工作量

另用手机实际 `/system/bin/simpleperf stat` 对原内联主线程 TID 计数，成组开启 `cpu-cycles:u,instructions:u`，同时读取 `task-clock`，每轮 30 秒。不与前述 FPS 或 FP 采样窗口重叠，不用 MHz 推算硬件计数。顺序为原实现 A、候选 B、恢复原实现 A。

| 官方 PMU 窗口 | 用户态退休指令，十亿 | 用户态 cycles，十亿 | task-clock ms | 既有状态 guest 增量 | 指令/guest，百万，近似 |
|---|---:|---:|---:|---:|---:|
| A2 | 85.76 | 32.94 | 24158 | 1212 | 70.76 |
| B2 | 82.57 | 32.11 | 23998 | 1211 | 68.18 |
| A3 | 87.84 | 33.73 | 24287 | 1205 | 72.90 |

这些是硬件实计数，不是样本占比。所有窗口 PSO/特化数量稳定；A2 的 PSO 为 256，B2/A3 为 257，均无编译增长，保留这个差异。既有 game-state 每秒一行，与工具计数边界不严格对齐，所以按 guest 归一化仅为近似。两次 A 本身也存在约 3% 的指令量差异。B 比两次 A 均低，近似每 guest 少 3.6%～6.5%，但不能把均值 5.07% 写成精确、独立的因果比例。

结合约 15,200 条事件变为零、planning 明确缩短、查询消费者仍生效，这支持“删掉了实际工作”，并不支持“优化只移动了成本”。PMU task-clock 仅下降约 0.7%～1.2%，工具报告的平均运行频率从 A 的约 1.36/1.39 GHz 到 B 的约 1.34 GHz；降低工作量不会保证 Running 时间等比例下降，更不会在其他阶段限制吞吐时自动涨帧。

工具尝试也保留原记录：第一次 `task-clock:u` 被内核拒绝，改为不带用户态修饰的软件事件后成功，硬件事件仍保留 `:u`。非 root app UID 无法通过 Simpleperf 启动子工作负载，最终使用已运行的目标 TID；工具内部可用性探测仍输出相关警告，但三轮正式计数均返回 0 并取得非零的硬件数据。每次按原值恢复 `security.perf_harden`，包括失败轮次；失败轮次没有算进上表。原数据与命令为 `PMU-A2/`、`PMU-B2/`、`PMU-A3/` 及 `official-PMU-comparison.json`。

## 官方 API 记录：是否增加 GPU 写回

使用已跑通的 GFXReconstruct API 结构捕获，各采六个真实提交/出图帧，独立于性能窗口。A/B 每帧分别 2,419/2,417 draw、两次 Vulkan submit，极少量动画绘制差异保留，未伪称完全相同调用序列。

两边附件组、尺寸、load/store 规则除一处外一致。差异是 1673×765 深度模板组中未写深度面的 `DONT_CARE` 变为 `NONE`，模板面仍 STORE；独立的 untouched-plane 规则起效，**没有新增显式 STORE**。不能称命令完全相同，也不能由这两个枚举断言硬件 DRAM 流量必然相同。

按格式/整渲染面积估算的逻辑 LOAD/STORE 均保持 122,761,100 / 166,207,670 字节/帧。这不是总线计数器或能耗测量。当前营地的全局 Store 前瞻没有带来额外的显式写回消除，不代表其他场景也不需要它。

## 证据与边界

新基线和官方源码注解在 `.local/logs/coherent-fast-cpu-v1/`。实验四组原 trace、SQL/CSV、工具原采样、源码注解、冷启动实际日志及每次原存档收条在 `.local/logs/store-index-cost-v1/`，核心汇总为 `comparison.json`。API 原始文件、捕获/恢复收条和结构汇总位于该目录 `api-tools/`。

此实验不构成全场景、长时间温度或硬件带宽认证。全部已结束真机进程均通过原生命周期确认存档 commits=2 后停止；工具设置按原值恢复。实验开关保持默认关闭，不因当前营地未涨帧就删除已证明的工作量节省，也不依据单场景把所有设备的 Store 分析默认关闭。

实验后恢复先前已通过两次桌面资格化的 `5d4b24c` canonical APK、原 profile 和 receipt；重新核对 APK 与六个资源/配置锚点的 SHA256。一次无 extras 的普通桌面启动再次进入真实营地，实际共享/lazy/精确字节/inline CPU7/stream reference 均生效，原保存 commits=2 后停止。当前输出仍为用户原 2358×1080/0.75，未将 benchmark 的显示参数写入默认。

该次恢复观察器随后因缺少 Android Java/Mesa INFO 启动日志而拒绝签发新资格收条，失败记录保留。实际 game-state 与当前 PID 原 native.log 可读；同 UID 的 shell 日志探针可见。一次尝试开启 OEM 日志控制被 ADB 拒绝，属性原值 `no` 未改变，没有申请 root 或扩大权限。`restoration-proof.json` 将“恢复同一已验收 tuple、普通游戏/存档通过”与“没有取得新的完整驱动日志资格”分开记录，**没有把失败的观察器写成通过**，也没有修改原发布校验。手机上保留的是原已验收版本，未留下实验 APK 或开启实验默认值。
