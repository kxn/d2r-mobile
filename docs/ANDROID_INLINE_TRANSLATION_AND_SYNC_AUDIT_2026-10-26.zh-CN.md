# 游戏线程内翻译实验与同步审查（2026-10-26）

这是上游 v2 对照后的进一步调查。用户要求停止复测之后，**没有再启动游戏或采集**；后续结论只来自已采集的 Perfetto/Simpleperf、源码和离线着色器检查。

## 已实现的实验及结果

代码分支 `codex/inline-shared-translation-v1`，基于实际安装包的源码 `1123f17`，两步提交：

- `6663b23`：游戏调用线程内执行 NVN 翻译，复用同一执行函数；所有提交、Present、FRAME、资源回读/关闭/缓存维护和生命周期收尾任务取得同一 FIFO 执行权。共享 Pool 的准入由“必须是专用 worker”改为“有串行执行保证”。GPU 完成仍由独立线程处理。
- `945aa34`：增加独立的启动期 CPU 核掩码参数，允许分别比较线程模式与调度；零掩码不干预 Android。只影响实际翻译/呈现线程，不绑定其他游戏线程或 GPU 完成线程。

没有更改游戏模块、规则产物、着色器或 native 资源包；这些模式使用同一个 APK 的冷启动选项。`inline_translation` 默认关闭，`translation_cpu_mask` 默认零，尚未作为所有场景的产品默认。原始游戏存档另有备份，每次停止均获得原生命周期的新 `commits=2` 确认。

固定输出 1968×900、3D 0.85、同角色同营地位置；定制 Turnip、共享 guest heap、lazy import windows、native 资源与异步 GPU 完成都实际开启。没有以关闭共享内存冒充线程对照。每组使用原 Perfetto 20 秒系统调度与游戏 Surface 数据，无抓帧层、额外应用计时器或窗口内模拟操作。

| 模式 | 两轮平均 FPS | 全应用 Running ms/上屏帧 | 游戏提交主线程 + 翻译线程 Running ms/帧 |
|---|---|---|---|
| 独立翻译线程，CPU 7 | 31.07 / 30.72 | 56.49 / 56.87 | 32.18 / 32.30 |
| 调用线程内翻译，CPU 7 | 31.11 / 31.06 | 43.85 / 45.40 | 23.44 / 24.20（同一线程） |
| 调用线程内翻译，Android 自行调度 | 31.20 / 31.16 | 43.09 / 43.12 | 25.90 / 25.99（同一线程） |

同核心两组全应用 Running 平均下降约 **21%**，帧率没有明显提升。CPU Running 是调度时间，受核心、频率、执行效率和工作量共同影响，不能称作退休指令数或功耗下降了 21%。它也不能单独证明锁竞争：阻塞等待不计入 Running，自旋、调度管理和缓存争用才可能增加执行成本。

未绑定核心的独立线程组曾降至 21.02 FPS，翻译线程平均主频约 1.07 GHz；此前同配置约 1.48 GHz。因此不拿这组与内联组相减，宣称无条件 50% 的涨帧收益。上游的“切线程模式就有 43 对 32 FPS”也不能直接外推成我们的结果。

功能验证：原 ARM64 NVN 执行器通过四个并发调用者、512 个任务的 FIFO/排他/调用线程身份检查；原 Vulkan acquire/fence 检查证明 GPU 尚未完成时栅栏仍不完成。它们是功能检查，不代替真实游戏结果。本机真实游戏已进入营地并连续运行各测试窗口，但没有完成该新路径的全场景/战斗验收。

产物：`.local/build/inline-shared-translation-v2/canonical.apk`，源码 `945aa34`，SHA-256 `a077f20a817bdd8d72e8b8f14739c91be4f64db93ef1e1868c6b1348ae533d26`。完整构建指纹、启动参数、准入状态、系统轨迹和保存确认在 `.local/logs/inline-shared-translation-v1/`。

## 同线程后哪些同步仍然多余

实验为了先保持时序正确，仍沿用原任务框架，尚未把它当成最终最省的实现：

- `x_push()` 的任务编号、队列互斥和完成广播仍在。
- 同步已执行完的 `x_wait()` 仍会取队列锁。
- Present 仍经任务票号表取回实际票号。
- `nvnQueueSubmitCommands()` 仍复制句柄数组，执行后释放。

这些原本服务于生产者/翻译 worker 的部分可以在内联专用路径中绕过，保留一次外层串行执行权和真实 NVN/GPU 栅栏语义。不能把所有锁直接删掉：其他游戏线程仍可做 Pool 注册、flush、关闭和回读；生命周期线程、GPU 完成线程也仍并发运行。

高频 `V.resources` 同时保护 owner 录制状态、资源注册表和完成侧 Pool 引用。更有意义的方向是分离访问者：owner 独占的工作数据不与完成侧共用可变字段，完成线程消费提交时固定的 cache-maintenance 描述，完成后的引用和临时对象由 owner 接回处理。须一起调整销毁等待与引用生命周期，否则仅推迟引用释放可能制造死锁，不能只删 mutex。

`completion_mu` 保护 pending/retired、完成序号与等待通知，仍有真实跨线程访问。当前源码在持这把锁时调用 `vkDestroyFence`，可作为缩小临界区的明确候选，但没有证据把这段驱动调用认定为整帧大瓶颈。

## 上游有没有收尾线程

有。上游 `xbg_game.cpp` 的 `poolreset` 线程默认在 Android 开启，流程是等待该槽位 GPU fence，再 `vkResetCommandPool`。查询结果、写回/事件公布、retire 回调和大部分描述符/临时资源回收仍在 `retire_slot()` 中进行。

我们的 `dm-gpu-complete` 线程则串行执行：

1. 等 fence。
2. 共享内存可见性维护、写回和事件回调。
3. 释放 GPU 使用引用、发布完成序号。
4. 重置命令池，再发布资源可复用。

它已经在不持资源锁时等 GPU，且普通完成通知早于命令池重置。源码仍有一种可能：前一批的 reset 会推迟 worker 去观察后一批 fence，但这只是待核对的排队机制，不能称作已证明的 7 ms 或 20 ms 成本。另有少量共享元数据和缓存回收实际仍由录制线程 `reclaim_submissions()` 完成，“有完成线程”不等于所有回收都移走了。

上游 `xbg_completion_wait.h` 的 Completion 是完成通知/争锁辅助类，不是另一个执行全部回收的线程；Android 与 Harmony 的默认启用策略还不同。

## 已有工具数据能排除什么

复用前次 OFF/ON 的独立 Perfetto 捕获，按原 `NVN command replay` 数归一化。它们属于此前源码/配置，不是这次内联模式的新计时：

| 已标注范围 | OFF / ON，ms/周期 | 边界 |
|---|---:|---|
| 提交队列锁获取 | 0.0176 / 0.0174 | 不是所有资源锁 |
| Present 队列锁获取 | 0.0017 / 0.0017 | 不包含驱动 Present 调用 |
| 命令池重置 | 0.5374 / 0.5287 | 完成线程，可与录制重叠，不能直接从整帧扣减 |
| CPU 结果发布 | 0.0665 / 0.0602 | 仅该 marker 覆盖的工作 |
| 资源上下文上限等待 | 未出现 / 未出现 | 不证明其他场景永不出现 |
| `vkQueuePresentKHR` 调用 | 7.0208 / 7.0041 | 驱动/WSI 调用墙钟，不等于锁竞争或 GPU shader 时间 |
| `vkQueueSubmit` 调用总量 | 1.0878 / 1.1172 | 所有本周期拆分批次合计 |

同批六个旧 CPU 用户态采样窗口，mutex/futex/spin-lock 名称的可识别叶样本约占 0.22–1.30%。采样较稀、只覆盖旧 NvN 线程，不能当作阻塞等待占比，也不能排除缓存争用；但它不支持把大量 Running 时间直接归给 pthread 锁函数。

当前内联 C1 轨迹中，主线程每帧 Running 23.44 ms，Sleeping 7.51 ms，Runnable 约 0.76 ms；该捕获的 blocked_function/waker 为空，不能凭睡眠时间指认某一把锁。下一步优先沿已有 Present、同步栅栏和资源复用路径核对，不再把队列锁获取与驱动内部等待混为一谈。

## 新的优先级：提交粒度和着色器处理

### 1. 先审查 Adreno 上的启发式提前提交

`--stream-submits` 当前默认开启；`stream_flush()` 在满足 draw 配额且能关闭 pass/query 的边界提交。最新这批状态增量是每个游戏提交周期 **7 次内部提交 + 1 次 guest 提交 = 8 次**，其中约 **6 次属于 stream split**。旧的 27 ms 报告记的是当时另一批数据的内部计数，不应无条件当成这次的值。

上游 `NVN PERF submits=1` 只计引擎的场景提交；其 `vulkan_present.cpp` 还有一次呈现 blit 的 `vkQueueSubmit`。因此比较全应用调用数应是约 8 对 2，不能把引擎计数与包含 Present 的总量直接当成 8 对 1。

差距仍然实质存在。每次拆分还会轮换 `submit_resources`，重置录制绑定状态，并在退役时清理 driver-last、descriptor-last、history epoch 和临时 arena。它会改变缓存有效范围和 CPU/驱动对象管理频率，不只是多花一次 submit API 的成本。GPU 通道切分的 tile 保存/装载成本另需工具验证，不能直接由次数推算带宽。

上游 [frame-overlap 实验](https://github.com/jhaizhou-ops/d2r-mobile/blob/195ae11dc70f1ba7735c6063e1ed81102e1dbf52/docs/android-notes/2026-10-17-frame-overlap.md) 确实测到按 pass 拆分增加 GPU 成本并移除了该策略。那些是其早期 defer=1 条件，不是本机收益证明，但足以把“在 Mali 有过收益，因此高通也默认开”改为分设备判断。

下一候选已有 `--no-stream-submits`，不需要重写后端；仅取消启发式拆分，保留真实 NVN flush、事件、CPU 可见结果和 Present 所需的提交。按用户要求，这次**没有执行**该性能对照，也没有全局修改 Mali 策略。

### 2. Fragment quad shuffle → fine derivatives

我们安装的 `9507875007c6` 链默认仍是 native subgroup，`quad_transfer_v1/v2` 不是上游导数算法。实际 compiler options 还开启了通用函数内联。

已将上游原 `xbg_spirv_quad_derivatives()` 离线用于这 6,931 个现有产物：发现 307 个直接 shuffle 候选，**0 个成功改写**；29 个被 module-contract 拒绝，278 个被 control-flow 拒绝，没有保留下来的 helper-call 候选。上游工具链明确记录：在片元 SHFL helper 被内联后，176 个 helper-call 形式无法再改写。因此不能简单在现有 SPIR-V 后加一个 pass 就算移植成功。

正确候选顺序是：保留翻译器原形式，先识别并证明片元 quad 数值交换，再做导数改写，之后按需进行原有内联与清理。计算着色器的编译器规避继续保留。该变换有数值重建的误差和控制流/非有限值边界，不能把任意整数或位模式 shuffle 变成导数；须沿正常工具链生成新指纹、反射/证明 sidecar 和着色器链，不能沿用旧产物的精确 SHA 证明。

### 3. 常量分量折叠与单写临时变量转发作为组合

前次离线检查已确认：我们的 3,017 个模块存在 29,838 处低位分量折叠命中，6,920 个模块还能转发临时变量。这不是运行时材质值猜测，而是代数上可证明的分量索引和定义使用关系。它与 quad 改写应一起审查处理顺序，但分别保留开关/来源，不能把别人的 GPU 百分比相加冒充本机结果。

这三项比“把看到的 mutex 全删掉”有更明确的结构性依据。单线程路径的无用交接仍应清理，GPU 完成线程的资源访问范围也应收窄，但不能把所有 CPU/GPU 同步一并删掉。
