# 上游 v2 Android Vulkan 真机对照（2026-10-26）

结论：上游在这台高通上确实更快；相同输出、固定 0.85 的营地对照约 **43.2 FPS 对 30.6–31.0 FPS**。不过，把同一个上游 APK 切成独立 NVN 翻译线程后，它也降到 **32.4 FPS**。恢复原模式又回到 **43.2 FPS**。下一步应优先检查翻译线程拓扑、任务交接与调度，而不是继续把全部差距归于 draw 内缓存或共享内存覆盖率。

## 版本、产物与边界

- 上游最新源码：`195ae11dc70f1ba7735c6063e1ed81102e1dbf52`；发布 APK：v2.0.0，源码 `b811b90172f4eb40ec1bc89d903308e0c5ab88d0`。
- 发布 APK SHA-256：`1ed3c029963797291833551722ed3bf7c5e4a00740b47ca48f9ae94a5fd76e8c`，核对发布的 SHA256SUMS。
- 我们的已安装 APK：`1123f17` 构建，SHA-256 `b0e3e4d3709cf6c7592d808af4f1e14eca6f6ba88f7050600704c50e105692db`；分段复用实验关闭，普通后端开启，Turnip f830 共享内存和 native ASTC 资源保持原配置。
- 真机：USB `10CG570J59001U1`，vivo V2528A / SM8635 / Adreno 735。不是上游报告的 Redmi K50 Ultra / 骁龙 **8+ Gen 1** / Adreno 730。未测试 Mali 或 6GB 平板。
- 上游使用原系统 Vulkan 驱动与原 BC 资源；我们使用定制 Turnip 与 native ASTC 资源。因此跨项目两行是产品路径对比，不能把所有差异归给一个后端函数。上游内部各控制组的 APK、驱动、资源和着色器一致。
- 没有改写游戏世界、人物属性或存档。上游每次从同一个原存档副本启动 Lv3 野蛮人，营地同位置；我们的原存档先备份，每次停止前均得到原生命周期 `commits=2` 的新确认。

官方未规避的 APK/着色器组合在本机两次启动都停在计算着色器 `098a126f92bf533a` 后崩溃（SIGSEGV，地址 0x48），与上游 [issue #123](https://github.com/jhaizhou-ops/d2r-mobile/issues/123) 的现象相符。第二次已排除资源和存档读写权限错误。随后采用上游最新提供的 `DM_VK_INLINE_CS=1` 离线选项，从未改写的原始 Update/ExeFS 重新加工：只有 **5 个计算着色器包**改变，两个游戏 CPU 模块与 release 构建逐字节相同；手机端全部 6,931 个着色器包及两个模块的 SHA-256 均核对通过。

下表上游运行成绩均指 **官方 APK + 上游 inline-CS 规避包**，不能称作未经任何规避的 release 开箱结果。没有自行修改游戏 binary。额外构建了 native 库与官方 APK 字节相同的可调试壳，但它未安装，也未参与成绩。

## 测量条件与结果

两边输出均为 **1968×900**，固定 `0.85`，上游日志确认 3D 为 **1673×765**。手机 Surface 为 2358×1080，未修改手机原来的屏幕 override。没有抓帧层、外推、改游戏状态或在采集窗口内模拟点击/截图。

使用现成 **Perfetto** 的调度、频率与 SurfaceFlinger 数据，复用已有 SQL；每组约 20 秒，以游戏 Surface 的 `PresentFenceSignaled` 连续间隔计算平均 FPS。CPU 是系统调度记录的 **Running 时间 / 上屏帧**，不是自行插入函数计时。各线程时间相加可大于整帧时间。

| 实验 | 平均 FPS | 上屏间隔 p50 / p95，ms | 全应用 CPU Running，ms/帧 |
|---|---:|---:|---:|
| 我们，原线程模式 | 30.60 | 33.22 / 33.23 | 48.13 |
| 我们，同配置复测 | 31.04 | 33.22 / 33.23 | 53.61 |
| 上游，默认同步翻译，绑定最快核心 | 43.19 | 22.15 / 33.22 | 38.59 |
| 上游，仅改 `DM_NVN_SYNC=0`，独立翻译线程 | 32.38 | 22.15 / 55.37 | 53.50 |
| 上游，同步翻译，仅关闭核心绑定 | 42.79 | 22.15 / 33.22 | 38.50 |
| 上游，恢复默认同步翻译和核心绑定 | 43.22 | 22.15 / 33.22 | 39.21 |

独立翻译模式下，上游的翻译线程仍全部运行在 CPU 7，因此不能把它的下降解释成“忘记把翻译线程放到大核”。关闭绑定的同步组约 75% 的关键线程 Running 时间仍由系统分配在 CPU 7，平均频率有所补偿；这里的绑定收益很小，不应照搬其 Redmi 上的百分比。

我们首次测量的翻译线程为 **23.86 ms Running/帧**，复测 **26.85 ms**；首次仅约 **3.64%** 的运行时间位于 CPU 7。上游同步组的关键线程包含游戏执行和翻译，约 **18.85–19.06 ms/帧**，范围不同，不能直接当作“同一个翻译函数从 24 ms 降到 19 ms”。核心、频率、调度、交接和后端工作均可能影响 Running 时间；本次没有指令计数证据，不能将 CPU 时间差冒充少执行的指令数。

上游默认动态比例另外实际运行过：本机在重场景营地会从 0.85 逐步降低至 0.60；这段日志不能混入固定比例成绩。上游详细公开报告也确有多次保持 0.85 的记录，不能反过来断言它的 60 FPS 都来自自动降比例。**本机固定 0.85 没复现 60 FPS；可以证实默认线程策略的明显优势。**

测量修正：SurfaceFlinger 可带入采集前的帧事件，`trace_bounds` 曾使第二次动态实验包含一个假的 27 秒间隔。已改用 Perfetto 服务自己的 `tracing_started_ns` / `tracing_disabled_ns` 裁窗，并对早期数据重新计算；固定比例各组均使用服务窗口。原输出保留审计，异常间隔不作为游戏卡顿结论。

## 代码上的真实差异和优先级

### 1. 先改变翻译与提交的组织方式

上游 Android 的 `jni_android.c` 默认 `DM_NVN_SYNC=1`，同一个提交线程执行原 NVN 翻译函数；`vulkan_present.cpp` 默认选取 `cpuinfo_max_freq` 最高的一组核心。其 GPU 帧重叠、延后事件与 Vulkan 完成处理仍存在。**HLE 同步翻译不等于每帧同步等待 GPU。**

本次同一上游后端由同步切到独立翻译再恢复的结果，是当前最强的宏观证据。尚不能把下降精确分配给哪把锁、哪次唤醒或 DVFS；需要沿任务生产、消费、取图/等待继续用调度轨迹定位。

我们已有 `DM_NVN_SYNC`，但共享路径有硬约束：

- `dm/gfx/nvn/hle_nvn.c`：`dm_gfx_shared_owner_ready()` 返回 `!g_x_sync`。
- `dm/gfx/vulkan/nvn_vk_shared_pool.inc`：探测共享内存时要求专用 NVN owner，否则回退。

因此下一组实验必须**保持共享内存与 native 资源实际启用**，将资源操作的串行归属与“固定是专用 worker”解耦；不能切同步后让共享退掉，再声称只改线程。先验证调用来源和队列归属，避免让后端无保护地被多个游戏线程同时进入。同步翻译只改变 CPU 翻译组织，不应撤掉独立 GPU 完成处理或把 Vulkan 变成逐帧 WaitIdle。

尝试从 ADB/run-as 外部设置我们线程亲和性，被手机拒绝（Permission denied）；没有伪称生效。对应采集已明确更名为未绑定的同配置复测。

### 2. 着色器常量索引折叠 + 单写临时变量转发

上游的 `xbg_spirv_ldc.cpp` / `xbg_spirv_temps.cpp` 有明确配套机制：通过整数低位推出常量缓冲分量下标，再将单次赋值临时变量转发，帮助驱动生成更直接的常量读取。它不把运行时材质值猜成常量。

已用**上游原实现**离线检查我们实际安装的 `9507875007c6` 着色器链：6,931 个 SPIR-V 中，**3,017 个模块存在 29,838 处折叠命中**；6,920 个模块可继续转发临时变量。说明我们现有工具链尚未完全消掉这些形式，值得做合并后的真实 GPU 对照。离线命中不是本机 FPS 收益，本次没有部署这些变换。上游公开约 10.7% 的 GPU 收益仅属于它自己的设备、条件和完整组合。

没有依据把当前差距归给我们此前的 quad-readonly 实验：本次实际 shader manifest 的编译选项没有启用该模式，不能仅看到源码支持它就断言它在热路径运行。

### 3. 对齐整体出图负担，再比较 GPU

上游产品基准以约 2000×900 输出，按设备宽高比得到本机 1968×900。我们过去常用 2750×1260、0.60 的能力测试：3D 像素数其实与本次 0.85 较接近，但 UI、最终合成及部分全分辨率处理的基准面积约为本次的 1.96 倍。不能只比较“0.60 对 0.85”判断谁画得更少。

本次固定输出后差距仍在，所以分辨率不是全部解释。需要在 CPU 组织模式对齐后，再用 GPU 工具核对着色器、渲染通道边界和带宽，不能拿某一步的时间当作 TBDR 上独立 draw 的代价。

### 4. 对回读、查询和资源准备按语义比较

上游 Android 关闭了“每次操作前完成全部待写结果”的预检；实际读取仍做地址范围重叠判断。其 `cpu_access()` 还明确允许两类 GPU 快照读取使用上一次已公布的遮挡统计，接受约一帧延迟。这与完全等价的当前结果转交不是同一种策略，应单独评估视觉与语义，不能未经审查全盘搬入。

我们的现有共享路径、范围同步、动态 storage 升级、按需 mutable-format、持久 PSO 和资源缓存已经覆盖不少同类方向；没有证据说“少一个缓存名字”就是大差距。上游在不注册任意 guest 内存的路径上更快，也说明共享内存并不足以抵消不合适的翻译组织方式。

## 复现与清理

完整本机材料在 `.local/logs/upstream-v2-comparison-20261026-v1/`：

- `pack-inputs.json`、`pack-outputs.json`、`inline-pack-outputs.json`、`inline-device-sha256.txt`：原始输入、规则、全产物及设备核验。
- `official-second-logcat.txt`：未规避的 release 崩溃；各组 `boot.log`：环境、比例、区域及加载过程。
- 各组 `trace.pftrace`、`analysis.sql`、`analysis.csv`；早期修正另存 `analysis-service-window.*`。`results.json` 汇总固定比例结果。
- `our-shader-upstream-fold-audit.csv`：只做离线检查的逐模块命中，不是运行时统计。
- `own-save-stop/result.json`、`own-repeat-save.json`：我们的两次保存确认；`cleanup.json`：任务游戏与工具进程均已停止。

两个上游源码工作树保持干净。官方包与我们包独立安装；原游戏和存档未覆盖。测试结束后上游环境恢复到默认动态比例和同步翻译（仅保留隔离存档路径与英文）。本次未把任何实验改成我们的默认实现，也未声称我们已经获得 43 FPS。
