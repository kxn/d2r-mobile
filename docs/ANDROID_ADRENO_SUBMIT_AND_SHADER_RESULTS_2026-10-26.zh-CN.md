# Adreno 提交粒度与上游着色器优化：完成实验结果

2026-10-26。接续同日的上游对照与线程/同步审查。本次用户明确要求完成真机实验，因而恢复了对照采集。结论：**减少启发式提交和调整着色器处理都有本机收益，但当前结果仍约 34 FPS，没有复现上游接近 60 FPS。**

## 固定条件与证据边界

- 同一台 USB 高通手机：vivo V2528A，SM8635 / Adreno 735，序列号 `10CG570J59001U1`。不是上游报告的 Adreno 730。
- 同一 APK，源码 `945aa34`，SHA-256 `a077f20a817bdd8d72e8b8f14739c91be4f64db93ef1e1868c6b1348ae533d26`。调用线程内翻译、CPU 7 掩码 `0x80`、独立 GPU 完成线程；定制 Turnip、真实共享 guest heap、lazy import windows、native 资源均确认启用。
- 输出 1968×900、3D 比例固定 0.85，Surface 2358×1080；没有靠再次降低分辨率取得收益。原角色、同营地区域 1、位置 5225/6289、等级 3、经验 2920，采集窗口内没有操作角色。
- 每组使用官方 Perfetto 的 20 秒调度/频率和游戏 Surface 数据；FPS 从实际完整上屏间隔计算，CPU 为调度 Running 时间。窗口内无抓帧注入、截图、点击、自定义计时器或其他 profiler。截图在窗口之后取得。轨迹健康查询没有报告丢失/错误记录。
- CPU 表中的全应用毫秒是各线程 Running 之和，不能当成单线程墙钟。所有结果均未固定 CPU/GPU 频率，不能把 Running 降幅写成指令数或能耗降幅；也没有用这些结果冒充 GPU pass 时间或实际 DRAM 带宽。
- 每次结束均经原 Android 生命周期获得新的 `commits=2` 存档确认，再停止游戏。Mali 没有参与、没有更改其策略。

本地原始记录在 `.local/logs/adreno-submit-granularity-v1/`，包括每组完整启动参数、准入状态、前后状态、Perfetto 轨迹/SQL/CSV、窗口后截图、保存确认、最终 `final-results.json` 及各文件哈希。采集脚本只编排现成工具并整理输出，不增加游戏内计时。

## 一、取消 Adreno 上的启发式提前提交

先保留旧着色器链 `9507875007c6`，仅切换已有的 `--no-stream-submits`。次序为 OFF1 → ON1 → OFF2 → ON2，其中 OFF 表示关闭启发式拆分。真实 NVN flush、事件、回读和 Present 所需的提交不取消。

| 组 | 启发式拆分 | FPS | 全应用 Running ms/上屏帧 | 翻译 owner Running ms/上屏帧 | 内部 submit/游戏提交周期 |
|---|---|---:|---:|---:|---:|
| OFF1 | 关闭 | 33.01 | 43.05 | 22.60 | 1.00 |
| ON1 | 开启 | 30.49 | 45.67 | 23.92 | 7.03 |
| OFF2 | 关闭 | 31.23 | 42.62 | 23.25 | 1.00 |
| ON2 | 开启 | 29.74 | 45.62 | 24.03 | 7.05 |

关闭后两轮 FPS 分别约提高 **8.3% / 5.0%**，全应用 Running/上屏帧下降 **5.7% / 6.6%**。所有四组的管线对象数在窗口内均保持 326，没有新增管线混入。

工作量检查：每游戏提交周期约 2416–2419 次 pipeline prepare，工作形状接近；启发式 split 从约 6 次降到零。加上 guest 提交，实际总量约 **8 → 2 次**，不是将所有提交去掉，也不能直接和上游仅计引擎的“一次”混比。

机制是减少批次及资源上下文轮换、绑定状态重置和退役管理。每周期 descriptor 分配调用约 0.90–0.96 → 0.22–0.23，但原本绝对量已很小。纹理准备仍约四千余次，说明**取消拆分没有消除每 draw 的整段资源准备**。没有硬件带宽证据证明此次收益具体来自多少 GMEM 落盘，不能由 submit 数反推。

决定：本机后续对照明确使用 `--no-stream-submits`，保留这个有效设置。没有全局替换 Mali 默认，更没有删除通用 NVN 同步。

## 二、上游着色器组合已接入并完成真机对照

实验源码分支 `codex/inline-shared-translation-v1`：

- `9740dbc`：固定上游 `195ae11dc70f1ba7735c6063e1ed81102e1dbf52` 的 quad/常量分量/单写临时变量处理源码与逐文件哈希，离线接入原工具链。
- `cf6a17d`：部署校验这些优化器的源码/工具指纹。
- `6959356`：以私有临时目录并行执行原来逐项验证；验证内容不变，部署测试 11 项通过。

开关分别为 `DMSH_VK_QUAD_DERIVATIVES=1`、`DMSH_VK_COMPONENT_FOLD=1`，后者包含分量折叠与单写临时变量转发。quad 只用于片元阶段。

关键处理顺序是：**先改写上游可证明的 quad helper，再执行我们原有的函数内联。** 对已经内联的旧产物追加该 pass 曾得到零命中；不能把这次正确接入当作同一种零命中实验。

### 真实生成与验证量

候选链 `29e56b51bce5` 从原始着色器输入通过正常 `dmsh_build.py` 生成，6931/6931 个模块通过验证：

| 项 | 全包 | 第一组游戏实际加载的 98 个 key |
|---|---:|---:|
| quad 改写 | 271 | 17 |
| 常量分量折叠 | 29,838 | 440 |
| 单写临时变量转发 | 1,566,347 | 13,765 |

`.spv` 总量约 447.58 → 355.04 MiB；现有 uniform specialization 的 `.spec` 总量约 191.14 → 190.25 MiB。因此不能用普通 SPIR-V 缩小 20.7% 宣称所有实际驱动输入或 GPU 指令也减少同样比例。

没有给已加工的 CPU 游戏 binary 叠补丁。输入清单记录原 NSO、162 个原始 shader pack、50 个 pipeline 输入及托管工具闭包；旧精确 SHA 的 `.dkey/.dspan/.plocal` 证明没有复用到不同 shader。重新生成的证明/反射通过原部署验证，52,240 个装机文件逐个核对哈希。独立测试：quad 35 项通过；分量折叠 20,000 输入等价检查通过；临时变量转发 2,000 输入等价检查通过。quad 有浮点重建误差边界，数值测试不代替所有游戏场景视觉验收。

构建选项、原始输入哈希、模块统计、全部产物哈希、设备哈希检查分别见本地 `shader-inputs.json`、`shader-combined-summary.json`、`shader-combined-deployment.json`。缓存切换也完整核对源目录文件哈希，不手改 shader 字节。

### 交错对照结果

所有组都关闭启发式拆分，保持相同 APK/共享内存/线程/分辨率。顺序 SH1 → REF1 → SH2 → REF2。

| 组 | 着色器 | FPS | 全应用 Running ms/上屏帧 | 翻译 owner Running ms/上屏帧 | owner 平均 MHz | 窗口内管线数 |
|---|---|---:|---:|---:|---:|---|
| SH1 | 新组合 | 33.72 | 41.36 | 22.07 | 1297.89 | 179 → 179 |
| REF1 | 原版 | 29.63 | 44.01 | 23.30 | 1200.16 | **167 → 174** |
| SH2 | 新组合 | 33.59 | 42.00 | 22.56 | 1218.88 | 172 → 172 |
| REF2 | 原版，已预热 | 31.25 | 43.32 | 23.00 | 1238.46 | 175 → 175 |

REF1 在采集期间新增 7 条管线，最长上屏间隔 88.62 ms，**不拿它计算稳态收益**。它被完整保留，没有隐藏。补测 REF2 后，最长间隔 33.24 ms；两个候选组最长也约 33.24 ms。

候选两组对预热原组约提高 **7.9% / 7.5%**，均值约 **7.7%**；全应用 Running/上屏帧低约 **4.5% / 3.1%**，owner 低约 **4.0% / 1.9%**。这支持本场景中保留该组合，但只有一个无新增管线的直接原版组，且 DVFS 未固定，不能称作全部场景严格保证的 7.7%，更不能把上游的 GPU 百分比挪作本机结论。

已查看原版与候选营地截图，角色、地面、屋顶、传送点和 UI 没有发现明显黑块或几何错误；没有完成该新 shader 组合的全部战斗/洞穴视觉验证。当前测的是组合，**不能将收益分别归给 quad、分量折叠或临时变量转发**。

## 当前保留状态与后续重点

1. 两个实验均有结果，不再停留在方案阶段。Adreno 对照保留关闭启发式拆分，保留新着色器组合；它们的百分比来自不同批次，不能直接相加作为总收益。
2. 手机已切回完整校验的新链 `29e56b51bce5`。原链保存为独立缓存目录，游戏已原生命周期保存并停止，没有后台空跑。源码和验证器保留在实验分支；内联模式默认开关、全设备 stream 默认和通用 shader 默认没有静默改写。
3. 真实最佳候选仍约 33.6–33.7 FPS。owner 的 Running 仍有 22 ms 左右，不能解释成只要删掉一把锁即可达到 60，也不能把此次 shader 收益当成“CPU 整段准备已经消失”。已有每 draw 准备次数仍很高，后续应继续检查执行结构、资源上下文有效范围，以及 owner/完成侧共享状态，优先删整段无用准备和交接，避免回到零散叶函数优化。
4. 下一次性能结论仍需将 owner Running、驱动/Present 等待和真实 GPU 硬件负载分开。当前这批 Perfetto 不提供纯 shader 成本，不据此宣布 CPU 或 GPU 单独限制。

复现时沿用本次完整启动参数（每组 `*-argv.json`），核心实验参数为 `--inline-translation --translation-cpu-mask 0x80 --no-stream-submits --game-res 1968x900 --scale-3d .85 --fixed-3d`，共享/native/provider 等准入参数同样必须保持，不得只复用这段缩写后声称配置完全一致。
